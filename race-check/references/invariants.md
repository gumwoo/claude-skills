# 불변식 고르기

동시성 시험은 "끝났을 때 무엇이 참이어야 하는가"를 정하는 순간 절반이 끝난다.
"에러가 안 나면 된다"는 불변식이 아니다. 경쟁 상태는 대부분 에러 없이 틀린 값을 남긴다.

## 자주 쓰는 네 가지

| 종류 | 예 | 읽는 곳 |
|---|---|---|
| 상한 | 판매 수량 ≤ 재고, 발급된 쿠폰 ≤ 100장 | `SELECT COUNT(*)` |
| 보존 | 남은 수량 + 판매 수량 = 처음 재고, 출금 합계 = 잔액 감소분 | 두 값을 함께 읽어 차이를 계산 |
| 유일성 | 한 사람이 같은 이벤트를 두 번 구매하지 않음, 좌석 하나에 홀드 하나 | `GROUP BY ... HAVING COUNT(*) > 1` |
| 응답과 저장의 일치 | 성공 응답 수 = 실제로 생긴 주문 수 | 응답 집계(`source: success`)와 DB 개수 비교 |

## 보존 법칙을 먼저 넣는다

상한만 보면 놓치는 경우가 있다. 앱이 남은 수량을 읽고 1을 빼서 다시 쓰는 코드(잃어버린 갱신)는
주문이 120건 생겨도 남은 수량이 0 이하로 내려가지 않을 수 있다. "남은 수량 ≥ 0"은 통과하는데
"남은 수량 + 판매 수량 = 재고"는 깨진다. 예시 서버에서도 이 불변식이 -199까지 벌어졌다.

## 응답만 믿지 않는다

`source: success`(성공 응답 개수)는 빠르고 설정이 쉽지만 서버가 말한 것일 뿐이다.

- 201을 돌려줬지만 트랜잭션이 나중에 롤백된 경우
- 409를 돌려줬지만 앞서 일부가 저장된 경우
- 비동기 처리(큐, 아웃박스)라 응답 시점에는 아직 저장 전인 경우. 이때는 불변식을 읽기 전에 처리가 끝날 때까지 기다리는 명령을 `cmd`에 넣는다.

그래서 응답 기반 불변식은 DB 기반 불변식과 함께 쓴다.

## 시작 상태

회차마다 같은 상태에서 시작해야 결과를 비교할 수 있다. `reset`에는 시험 데이터만 지우는 명령을 쓴다.
`TRUNCATE`나 `DELETE FROM orders`처럼 전체를 지우는 명령은 시험 전용 DB일 때만 쓴다.
공유 개발 DB라면 시험용 이벤트 ID 하나를 정해 그 행만 되돌린다.
