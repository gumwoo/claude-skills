인자: $ARGUMENTS

인자가 `run`으로 시작하면 "4. 실행"만 하고 결과를 보고한다. 아니면 처음부터 진행한다.

실행기는 `${CLAUDE_SKILL_DIR}/scripts/race.mjs`다. Node.js 22 이상만 있으면 되고 외부 패키지는 쓰지 않는다.

## 원칙

- 운영 환경에는 요청을 보내지 않는다. 실행기는 localhost·`*.localhost`·`*.test`만 기본 허용하고, 이름에 prod·production·prd·live가 들어간 호스트는 어떤 옵션으로도 거부한다. 스테이징에 보내야 하면 사용자가 그 호스트를 확인한 뒤 `--allow-host`로 연다.
- 통과는 증명이 아니다. 경쟁 상태는 확률적이라 "10회 중 0회 위반"이라고 쓰고 "동시성 문제가 없다"고 쓰지 않는다.
- 불변식은 가능하면 응답이 아니라 DB나 조회 API에서 읽는다. 응답은 거짓말을 할 수 있다(201을 줬는데 저장이 안 된 경우, 409를 줬는데 저장된 경우).
- 코드만 읽고 "락이 있으니 안전하다"고 결론 내지 않는다. 실행한 결과로 말한다.
- `race.json`의 `reset.cmd`와 불변식 `cmd`는 셸에서 그대로 실행된다. 이 대화에서 만들었거나 사용자가 직접 쓴 설정만 실행한다. 다른 곳에서 받은 설정이면 먼저 열어서 명령을 사용자에게 보여 준다.

## 1. 대상 찾기

공유 상태를 읽고 → 판단하고 → 쓰는 코드를 찾는다. 흔한 모양:

- 남은 수량을 조회한 뒤 0보다 크면 차감 (`if (stock > 0) stock -= 1; save()`)
- 이미 했는지 조회한 뒤 없으면 생성 (`if (!exists(user)) insert(user)`)
- 잔액을 읽고 계산한 값을 그대로 저장 (`balance = balance - amount; save()`)
- 상태를 확인하고 전이 (`if (status == PENDING) status = PAID`)

엔드포인트마다 지켜져야 할 것을 한 문장으로 적는다. 고르는 법은 `references/invariants.md`.

## 2. 실행 환경 준비

- 앱을 로컬(또는 사용자가 지정한 개발 환경)에서 띄운다. 실제 DB 엔진을 쓰는 환경이어야 한다. 테스트용 인메모리 DB는 락 동작이 달라 결과를 믿을 수 없다.
- 회차마다 같은 시작 상태로 되돌리는 방법을 정한다: 리셋 API, 또는 `psql`·`mysql`·`redis-cli` 명령.
- 인증이 필요하면 테스트 사용자 토큰을 여러 개 준비해 `vars`에 넣는다. 토큰이나 비밀번호를 대화에 출력하지 않는다.
- 앱을 띄울 수 없으면 여기서 멈추고 무엇이 없는지 보고한다. 실행 없이 결론 내지 않는다.

## 3. 설정 쓰기

`${CLAUDE_SKILL_DIR}/templates/race.json`을 프로젝트(예: `tests/race/`)로 복사해 채운다.

- `concurrency`: 재고보다 넉넉히 많게(재고 100이면 200). 1인 1회 제한을 보려면 `{{i % N}}`으로 같은 사용자를 일부러 겹치게 한다.
- `rounds`: 10 이상. 회차가 여럿이면 `reset`이 반드시 있어야 한다.
- `invariants`: 최소 하나는 DB나 조회 API에서 읽는다. 보존 법칙(남은 수량 + 판매 수량 = 재고)이 가장 많이 잡는다.

## 4. 실행

먼저 같은 요청을 하나씩 보내 기준을 확인한다.

```bash
node "${CLAUDE_SKILL_DIR}/scripts/race.mjs" tests/race/buy.race.json --sequential --rounds 2
```

순차 실행에서 위반이 나오면 경쟁 상태가 아니라 로직이나 불변식이 틀린 것이다. 그걸 먼저 고치거나 불변식을 다시 정한다.

그다음 동시에 보낸다.

```bash
node "${CLAUDE_SKILL_DIR}/scripts/race.mjs" tests/race/buy.race.json
```

- 종료 코드: 0 = 모든 회차 통과, 2 = 위반 있음, 1 = 판단할 수 없음(무효 회차, 불변식 확인 실패, 허용되지 않은 호스트, 설정 오류).
- 성공한 요청이 0건이거나 연결 오류·시간 초과가 요청의 10%를 넘은 회차는 "무효"로 표시된다. 요청이 제대로 가지 않았으니 그 회차의 통과는 의미가 없다. 인증·URL·본문·서버 상태를 먼저 고친다.
- 불변식 값이 비어 있거나(0행, NULL) 숫자가 아니면 0으로 읽지 않고 확인 실패로 처리한다.
- 출발 간격이 50ms를 넘으면 경고가 뜬다. 동시성이 약했다는 뜻이니 결과를 그만큼 낮춰 읽는다. 본문이 없는 요청(GET, DELETE)은 마지막 바이트를 붙잡아 둘 수 없어서 연결되는 순서대로 나간다.

## 5. 고치기

위반이 나오면 `references/fixes.md`에서 상황에 맞는 방법을 고른다. 우선순위:

1. DB 한 문장으로 끝내기: 조건부 `UPDATE ... WHERE remaining > 0`, 영향받은 행 수로 성공 판단
2. DB 제약으로 막기: 유니크 인덱스, CHECK 제약
3. 행 잠금: `SELECT ... FOR UPDATE`
4. 낙관적 잠금: 버전 컬럼 + 재시도
5. 분산 락·Redis는 DB만으로 안 될 때

애플리케이션 메모리의 락(`synchronized`, `Mutex`)은 서버가 두 대 이상이면 소용없다. 고친 뒤에는 순차 실행과 동시 실행을 둘 다 다시 돌린다. 같은 설정으로 3번 고쳐도 위반이 남으면 멈추고 보고한다.

## 6. 보고

- 고치기 전과 후의 결과: "10회 중 10회 위반, 재고 100에 최대 200개 판매 → 10회 중 0회 위반, 매회 정확히 100개"

- 만든 설정 파일 경로. 다음에 같은 시험을 다시 돌릴 수 있게 남긴다.
