# race-check

재고 차감, 좌석 선점, 쿠폰 발급처럼 공유 상태를 바꾸는 API에 같은 요청을 한꺼번에 보내고, 끝난 뒤 지켜져야 할 조건이 실제로 지켜졌는지 확인하는 skill입니다. 깨지면 고치고, 같은 시험을 다시 돌려 확인합니다.

재고 100개짜리 선착순 구매 API에 200명이 동시에 요청하면 이렇게 나옵니다. 같은 서버에 요청을 하나씩 차례로 보내면 매번 정확히 100개가 팔립니다.

```
$ node scripts/race.mjs examples/ticket.race.json

대상 POST http://localhost:4100/events/1/buy · 동시 요청 200 · 10회

  1회  위반     응답 201×199 409×1  출발 간격 4.1ms
  2회  위반     응답 201×198 409×2  출발 간격 6.1ms
  3회  위반     응답 201×200  출발 간격 4.0ms
  …
 10회  위반     응답 201×200  출발 간격 2.9ms

불변식
  위반  판매 수량이 재고를 넘지 않음  기대 <= 100, 실제 198–200, 10회 중 10회 위반
  위반  남은 수량 + 판매 수량 = 재고  기대 == 0, 실제 -199–-196, 10회 중 10회 위반
  위반  한 사람이 두 번 구매하지 않음  기대 == 0, 실제 48–50, 10회 중 10회 위반
  위반  성공 응답 수가 재고를 넘지 않음  기대 <= 100, 실제 198–200, 10회 중 10회 위반

결과: 10회 중 10회 불변식 위반
```

남은 수량을 읽고, 앱에서 1을 빼고, 다시 쓰는 코드였습니다. 조건부 `UPDATE ... WHERE remaining > 0` 한 문장과 (이벤트, 사용자) 유니크 제약으로 바꾸면 같은 시험에서 10회 모두 정확히 100개가 팔리고 100명은 409를 받습니다.

## 사용법

```
git clone https://github.com/gumwoo/claude-skills.git
cp -r claude-skills/race-check ~/.claude/skills/
```

설치해 두면 선착순·예약·재고·결제 로직을 만들거나 "동시에 눌러도 괜찮아?"라고 물을 때 Claude가 알아서 씁니다. 이미 만든 설정으로 실행만 할 수도 있습니다.

```
/race-check run tests/race/buy.race.json
node ~/.claude/skills/race-check/scripts/race.mjs tests/race/buy.race.json --sequential
```

skill은 이 순서로 진행합니다. 읽고-판단하고-쓰는 코드를 찾고, 끝났을 때 참이어야 할 조건(불변식)을 정하고, 앱을 로컬에서 띄운 뒤 설정 파일을 씁니다. 그다음 요청을 하나씩 보내 기준을 확인하고, 동시에 보내 비교합니다. 위반이 나오면 고치고 둘 다 다시 돌립니다.

설정은 JSON 하나입니다. 요청 본문의 `{{i % 150}}`처럼 요청마다 값을 바꿀 수 있고, 불변식은 DB 명령(`psql -tAc ...`), 조회 API, 응답 상태 코드 개수 중에서 고릅니다. 회차마다 같은 상태로 되돌리는 `reset`도 넣습니다. 예시는 [templates/race.json](templates/race.json)에 있습니다. Node.js 22 이상만 있으면 되고 외부 패키지는 없습니다.

## 만들면서 고민한 것

계기는 7월에 나온 [글](https://blog.alexrusin.com/claude-code-race-condition/) 하나였습니다. Claude Code가 만든 예약 API가 테스트를 다 통과했는데, 같은 좌석에 요청 두 개를 동시에 보내자 둘 다 성공했습니다. 에이전트는 요청 하나를 기준으로 코드를 읽고 테스트도 그렇게 짜기 때문에, 요청 사이에서 생기는 문제는 스스로 잘 보지 못합니다.

찾아보니 동시성을 다루는 skill은 이미 여럿 있었습니다. 다만 대부분 배리어로 스레드를 맞추는 법, 격리 수준 표, 락 고르는 법 같은 지침이었고, k6 skill들은 응답 속도를 쟀습니다. HTTP 요청을 실제로 한꺼번에 보내고 끝난 뒤 DB에서 "몇 개가 팔렸나"를 확인하는 실행형은 찾지 못했습니다. 이 skill은 그 부분을 맡았습니다.

설계하면서 정한 것들입니다.

- **순차 실행을 먼저 돌립니다.** 같은 요청을 하나씩 보냈을 때도 불변식이 깨지면 경쟁 상태가 아니라 로직이나 불변식이 틀린 것입니다. 예시 서버는 순차로는 매번 통과하고 동시로는 매번 위반합니다. 이 대비가 있어야 "동시성 버그"라고 말할 수 있습니다.
- **불변식은 DB에서 읽습니다.** 응답 코드만 세면 서버가 말한 것을 믿는 셈입니다. 보존 법칙(남은 수량 + 판매 수량 = 재고)을 같이 넣으면 잃어버린 갱신까지 잡힙니다. 위 서버를 한 번 돌린 뒤 조회해 보면 주문은 200건인데 남은 수량은 99입니다. "남은 수량 ≥ 0"만 봤다면 통과했을 것이고, 보존 법칙은 -199로 벌어집니다.
- **요청이 제대로 안 간 회차는 통과로 치지 않습니다.** 토큰이 틀려 200개가 전부 401을 받으면 불변식은 당연히 지켜집니다. 그래서 성공이 0건이거나 연결 오류가 요청의 10%를 넘은 회차는 "무효"로 표시하고, 위반이 없어도 종료 코드 1을 냅니다. 불변식 값이 비어 있을 때(0행, NULL)도 0으로 읽지 않고 확인 실패로 처리합니다.
- **운영 환경에는 보내지 않습니다.** 기본으로 localhost와 `*.localhost`, `*.test`만 허용하고, 이름에 prod·production·prd·live(뒤에 숫자가 붙어도)가 들어간 호스트는 `--allow-host`로도 열리지 않습니다. 호스트는 `{{}}`를 채운 뒤의 실제 URL로 모든 요청마다 확인하고, 조회 API의 리다이렉트는 따라가지 않습니다. 두 번째 skill(infra-change-guard)과 같은 원칙입니다.
- **결과를 "안전하다"고 쓰지 않습니다.** 경쟁 상태는 확률적이라 "10회 중 0회 위반"처럼 횟수로만 보고하게 했습니다.

요청을 보내는 방식은 연결을 모두 연 뒤 본문의 마지막 1바이트만 남겨 두었다가 한꺼번에 보내는 방식(last-byte sync)을 썼습니다. 서버는 마지막 바이트를 받아야 요청을 처리하기 시작하니 출발 시점이 맞춰집니다. 본문이 없는 GET·DELETE 요청은 붙잡아 둘 바이트가 없어서 연결되는 대로 나갑니다. 다만 솔직히 적자면, 예시 서버에서는 `Promise.all`로 `fetch` 200개를 쏘는 단순한 방식도 위반을 똑같이 잡았습니다. 이 skill의 쓸모는 요청을 보내는 기교보다 회차마다 상태를 되돌리고, DB에서 불변식을 읽고, 순차 실행과 비교하고, 운영을 막는 쪽에 있습니다.

## 어떻게 확인했나

`node tests/run-tests.mjs`로 49개 시험을 돌립니다. 호스트 판정(prod가 단어 일부인 `productivity`는 통과), 설정 검사, 요청 값 채우기를 확인합니다. 시험용 서버로 본문 도중 끊기는 응답, 일부 연결 끊김, 전부 500, null 값, 리다이렉트 같은 상황도 만들어 봅니다. 그리고 [examples/ticket-server.mjs](examples/ticket-server.mjs)를 실제로 띄워 결과를 봅니다.

예시 서버는 프로세스 4개가 SQLite 파일 하나를 같이 씁니다. `--mode naive`는 흔히 처음 짜는 모양이고, `--mode fixed`는 조건부 UPDATE와 유니크 제약을 씁니다. 실제 서비스는 DB가 다른 서버에 있어서 읽기와 쓰기 사이에 왕복 시간이 생기는데, 이걸 `--gap`(기본 5ms) 대기로 흉내 냈습니다. 시험에서는 naive가 동시 요청에서 3회 모두 위반하고, 같은 서버가 순차 요청에서는 통과하고, fixed는 3회 모두 정확히 100개를 파는지 봅니다.

빈 폴더에서 `claude -p`로 실제 세션도 두 번 돌렸습니다. skill 이름은 말하지 않았습니다.

- **버그가 있는 쿠폰 서버를 주고 "요청이 몰려도 괜찮은지 확인하고 고쳐 줘"라고 했습니다.** 캠페인당 50장, 1인 1장 제한이 있는 서버이고, 남은 수량을 읽고 판단한 뒤 앱에서 계산한 값으로 덮어쓰는 구조였습니다. Claude는 skill을 불러 순차 실행(매회 정확히 50장)과 동시 실행(10회 모두 186~200장 발급, 중복 수령자 66~80명)을 비교했습니다. 원인을 세 가지로 짚었고, 유니크 인덱스, 조건부 UPDATE, 한 트랜잭션으로 고쳐 10회 중 0회 위반을 확인했습니다. 시키지 않았는데 "프로세스 하나에서는 JS가 순서를 맞춰 준 것일 수 있다"며 같은 DB를 쓰는 서버 2개 앞에 프록시를 두고 한 번 더 돌렸습니다. 결과물은 제가 따로 다시 돌려 봤습니다. 원본은 5회 모두 위반, 고친 코드는 5회 모두 통과였습니다.
- **"좌석 예매 서버를 만들고 동시에 눌러도 되는지 확인해 줘"라고 했습니다.** 이번에는 Claude가 처음부터 DB 제약으로 짜서 고칠 것이 없었습니다. 시나리오 3개를 순차와 동시로 각각 돌려 30회 중 0회 위반을 보고했고, "통과는 증명이 아니다", "프로세스 여러 개는 돌려 보지 않았다"를 확인하지 못한 것으로 따로 적었습니다.

만들면서 검사기 자체를 고친 것도 있습니다. 처음에는 회차마다 새 연결을 200개씩 열었더니, 비교 실험을 몇 번 돌린 뒤 Windows의 임시 포트가 바닥나 요청 대부분이 `EADDRINUSE`로 실패했습니다. 성공이 거의 없으니 불변식은 통과로 나왔습니다. 지금은 연결을 회차 사이에 재사용합니다. 요청이 제대로 안 간 회차를 무효로 처리하게 된 것도 이 일 때문입니다.

다 만든 뒤에는 제 판단을 알려 주지 않은 별도 에이전트에게 코드 리뷰를 맡겼습니다. 거기서 실제로 재현된 문제가 네 가지 있었습니다.

- `psql`이 0행을 돌려줘 출력이 비면 `Number("")`가 0이 되어 `== 0` 불변식이 저절로 통과했습니다. 조회 API의 `null`도 마찬가지였습니다.
- 호스트 확인을 `{{}}`를 채우기 전 URL로 하고 있어서, `http://{{var.h}}.localhost`에 운영 주소를 넣으면 차단을 피해 갔습니다.
- 서버가 응답 헤더를 보낸 뒤 본문 도중에 연결을 끊으면 끝나지 않고 멈췄습니다.
- reset 요청 본문을 보낼 때 content-type을 붙이지 않아서, Spring의 `@RequestBody`가 415를 돌려줄 상황이었습니다.

그 밖에 1회차만 성공하고 나머지 회차가 연결 오류로 실패해도 통과로 나오는 문제, `status:2xx`처럼 잘못 쓴 설정이 조용히 0으로 세지는 문제도 있었습니다. 모두 고쳤고, 각 문제가 다시 생기지 않는지 보는 시험을 위 49개에 넣었습니다. 고친 뒤 같은 리뷰어에게 다시 맡겨 여섯 가지가 모두 막힌 것을 재현으로 확인했고, 그때 새로 나온 문제(순차 실행에 마감 시간이 없어 1바이트씩 흘리는 서버 앞에서 멈춤)와 자잘한 것 넷도 고쳤습니다. 고친 뒤 같은 리뷰어에게 다시 맡겨 여섯 가지가 모두 막힌 것을 재현으로 확인했고, 그때 새로 나온 순차 실행 마감 시간 문제와 자잘한 것 넷도 고쳤습니다.

## 한계

- HTTP API만 대상입니다. 메시지 큐 소비자, 배치 작업, gRPC는 직접 시험 코드를 써야 합니다.
- 한 대의 컴퓨터에서 보냅니다. 출발 간격은 보통 수 ms인데, 1ms 미만의 아주 좁은 틈에서만 생기는 경쟁은 놓칠 수 있습니다. 예시 서버에서 왕복 지연을 0으로 두면 회차에 따라 잡히기도 하고 안 잡히기도 했습니다.
- 서버가 한 대인 로컬 환경에서 통과해도 여러 대로 띄우면 깨질 수 있습니다(애플리케이션 메모리 락이 대표적). 가능하면 로컬에서도 인스턴스를 두 개 이상 띄워 시험합니다.
- 통과는 그 설정, 그 횟수에서 위반이 안 나왔다는 뜻입니다. 동시성이 안전하다는 증명이 아닙니다.
