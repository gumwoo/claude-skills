# review-verify

다른 AI나 동료가 쓴 코드 리뷰를 받았을 때, 리뷰의 주장을 하나씩 지금 코드·테스트·CI와 대조해 판정하는 skill입니다. 판정은 맞음, 부분, 틀림, 이미 고쳐짐, 확인 못 함 다섯 가지입니다. 고치라고 하면 맞는 것만 재현하고 고친 뒤, 문서를 바뀐 코드에 맞추고 PR 본문 수정안을 냅니다(PR 본문은 허락할 때만 바꿉니다).

리뷰를 붙여넣으면 먼저 리뷰가 깔고 있는 전제부터 확인합니다. 리뷰어가 본 커밋은 무엇인지, 인용한 파일·줄·이름이 지금 코드에 실제로 있는지를 스크립트로 대조합니다. 아래는 시험용 저장소에서 다른 AI 리뷰를 대조한 결과입니다(일부).

```
$ node scripts/anchors.mjs review.md

커밋
  BEHIND    16d43ac      HEAD보다 1커밋 앞선 시점입니다. 그 뒤에 바뀐 파일 1개  ← 리뷰어가 본 시점으로 추정
            바뀐 파일: src/order.js

파일
  OK        src/coupon.js:3-5
            지금 3행: const left = await store.getRemaining();
  OK        src/order.js:10  [리뷰 뒤 이 줄 바뀜]
            리뷰 시점 10행: await store.cancelPayment(order.id, order.total);

코드 이름
  OK        issueCoupon() ("issueCoupon"로 찾음)  5곳/2파일: src/coupon.js:2, test/coupon.test.js:4, …
  OK        cancelOrder() ("cancelOrder"로 찾음)  3곳/2파일: src/order.js:1, test/order.test.js:4, …
  MISS      CouponPolicy.validateLimit()  HEAD에도, 이력에도 없는 이름입니다
```

리뷰어는 한 커밋 전 코드를 봤습니다. 환불 지적이 가리키는 줄은 그 뒤에 바뀌었고, 리뷰가 언급한 `CouponPolicy.validateLimit()`는 저장소 어디에도, 이력에도 없습니다. 같은 리뷰를 skill 이름 없이 "이거 맞는말이니?"라고만 물었을 때 Claude가 낸 판정은 이랬습니다(`claude -p`, 일부).

```
1. 🔴 issueCoupon() 동시 요청 시 초과 발급          맞음 — 재현: 재고 10, 동시 100건 → 100건 성공, remaining 9
2. 🔴 refund()가 amount 무시, order.total로 전액 취소  이미 고쳐짐 — d7f9461. 지금은 cancelPayment(order.id, amount)
3. 🟡 cancelOrder() 재취소 시 이벤트 두 번 발행        틀림 — src/order.js:2에서 CANCELLED면 return false.
4. 🟡 CouponPolicy.validateLimit()로 모아야 함       틀림(근거 없음) — CouponPolicy/validateLimit는 HEAD에도 git 이력에도 없음.
머지 판단: 리뷰는 "1, 2번 고치면 머지" → 실제로 남은 것은 1번뿐
```

## 사용법

```
git clone https://github.com/gumwoo/claude-skills.git
cp -r claude-skills/review-verify ~/.claude/skills/
```

설치해 두면 리뷰를 붙여넣고 "이거 맞는말이니?", "맞는지 확인하고 고쳐 줘"라고 할 때 Claude가 씁니다. 직접 부를 수도 있습니다.

```
/review-verify            # 판정하고, 고칠지 묻는다
/review-verify check      # 판정만. 코드·커밋·PR은 건드리지 않는다(리뷰 사본만 .git/review-verify/에 남긴다)
/review-verify fix 42     # PR #42 기준으로 판정하고 맞는 항목을 반영한다
```

skill은 모드 정하기, 리뷰를 주장으로 쪼개기, 기준 맞추기, 판정, 반영, 문서 맞추기, CI 확인, 보고 순서로 진행합니다. "맞는말이니?"처럼 묻기만 하면 판정에서 멈추고, 무엇을 어떻게 고칠지 적어 반영할지 묻습니다. 커밋, push, PR 본문 수정은 시켰을 때만 합니다. 판정 기준과 예시는 [references/verdicts.md](references/verdicts.md)에 있습니다.

스크립트는 두 개입니다. Node.js 22 이상과 git만 있으면 되고(PR 상태는 `gh`도 필요), 외부 패키지는 없습니다. 둘 다 저장소를 바꾸지 않습니다(`pr-state --body-out`은 지정한 파일에 PR 본문을 씁니다).

- `scripts/anchors.mjs <글>`: 리뷰나 PR 본문에 나온 커밋 SHA, 파일·줄 번호, 백틱과 코드 블록 안의 이름이 지금 저장소에 있는지 대조합니다. 리뷰어가 과거 커밋을 봤다면 줄 번호를 그 시점 기준으로 맞춰 보고, 그 줄이 그 뒤에 바뀌었는지 알려 줍니다. ```` ```suggestion ```` 블록처럼 리뷰가 새로 만들자고 한 이름은 "없음"으로 세지 않고 따로 보여 줍니다. ```` ```diff ````의 `+` 줄은 제안일 수도 PR 변경을 인용한 것일 수도 있어서, 지금 없는 이름이면 "확인 필요"로 따로 보여 줍니다.
- `scripts/pr-state.mjs [PR]`: PR HEAD와 로컬 HEAD가 같은지, 커밋 안 한 변경이 있는지, 그 HEAD에서 어떤 체크가 돌았는지 봅니다. PR HEAD의 워크플로 파일에서 `pull_request`·`push` 조건(`paths`·`branches`·`types`)을 읽어, 돌았어야 하는데 안 돈 워크플로와 필터 때문에 안 돈 워크플로를 나눠 보여 줍니다.

## 만들면서 고민한 것

이 skill도 제 작업 기록에서 나왔습니다. 개인 프로젝트에서 Claude Code에 직접 입력한 요청 8,441건을 훑어서, 다른 AI의 리뷰나 의견을 붙여넣고 "이거 맞는말이니?"라고 묻는 요청을 정규식으로 골라 보니 110건쯤 됐고, 그중 94건이 개발 프로젝트 두 곳의 PR 리뷰였습니다. 대부분 같은 루프였습니다. 다른 AI가 PR을 리뷰하면 제가 그걸 붙여넣고, Claude가 확인하고 고쳐 push하면, 다른 AI가 새 HEAD를 다시 리뷰하는 식입니다.

그 110건에 대한 Claude의 답을 보니, 첫 문장이 "맞습니다", "둘 다 맞다"로 시작하는 답이 54건이었습니다. 실제로 맞는 경우가 많긴 했지만, 확인하기 전에 결론부터 쓰는 모양이었습니다. 다음 회차에 리뷰어가 또 문제를 찾은 경우도 28건 있었습니다(이 숫자들도 정규식으로 센 것이라 대략입니다). 다시 찾은 문제를 읽어 보니 몇 가지가 되풀이됐습니다.

- 리뷰를 반영하면서 새 구멍을 만들었습니다. 중복 요청을 막으려고 "같은 키면 뒤엣것을 버린다"로 고쳤는데, 내용이 다른 두 요청 중 무엇이 남을지가 입력 순서에 달리게 됐습니다.
- 커밋 설명과 실제 코드가 반대로 동작했습니다.
- 코드는 26개로 바꿨는데 README에는 24개가 남았습니다.
- "CI 전부 성공"이라고 했는데 정작 바뀐 코드를 검사할 워크플로가 경로 필터 때문에 돌지 않았습니다.

리뷰 쪽 오류도 있었습니다. 옛 HEAD를 보고 쓴 지적, 실제로는 로컬에서 테스트를 돌렸는데 "테스트를 못 돌렸다"는 전제 같은 것들입니다.

찾아보니 같은 문제를 다루는 skill이 이미 있었습니다. obra/superpowers의 [receiving-code-review](https://github.com/obra/superpowers)는 여러 곳에 퍼져 있고, 핵심 규칙("동의부터 하지 말고 코드로 확인한 뒤 답하라")은 이 skill과 같습니다. 그래서 그 규칙을 다시 쓰기보다, 제 기록에서 실제로 틀린 지점을 기계로 확인하는 데 집중했습니다. 리뷰가 본 시점, 인용한 이름과 줄, CI가 실제로 돌았는지가 그것입니다. "이미 고쳐짐"을 "틀림"과 나눈 것도 그래서입니다. 리뷰어가 옛 HEAD를 봤다면 리뷰어는 틀린 게 아닙니다.

문제는 맞는데 제안된 고침이 틀린 경우도 자주 있었습니다. 예를 들어 리뷰가 제안한 대로 고치면 이전 PR에서 세운 약속("새 요청이 거절돼도 앞 요청 관찰은 유지한다")이 깨졌습니다. 그래서 지적과 제안을 따로 판정합니다.

## 어떻게 확인했나

`node tests/run-tests.mjs`로 166개 시험을 돌립니다. 시험은 임시 git 저장소와 가짜 `gh`로 두 스크립트를 확인합니다.

만드는 중에 시험이 가끔 실패했습니다. 매번 깨지는 시험이 달라서 깨질 때까지 반복해 돌려 보니, 커밋 SHA 앞 7자리가 `0332824`처럼 숫자로만 된 회차였습니다. 숫자만으로 된 것은 SHA로 보지 않게 해 두었기 때문인데, 짧은 SHA의 약 4%가 그렇습니다. 지금은 숫자만 또는 글자만으로 된 것은 후보로 두고, 저장소에 그 커밋이 있을 때만 SHA로 셉니다. 그런 커밋이 나올 때까지 빈 커밋을 만들어 확인하는 시험도 넣었습니다.

제 개인 프로젝트에도 읽기 전용으로 돌려 봤습니다.

- **세션 기록에 있던 실제 리뷰 원문 두 개.** 리뷰가 본 HEAD로 돌리면 인용한 이름 11개를 모두 찾았습니다. 다음 커밋으로 돌리면 "리뷰어가 본 시점은 1커밋 전"이라고 잡았습니다. 처음엔 6개만 찾았습니다. `@Valid / @NotNull / @NotBlank`처럼 한 백틱에 여러 이름을 쓴 것과 코드 블록 안의 `cancelActiveRun()` 같은 호출을 놓쳤기 때문인데, 고친 뒤 11개가 됐습니다.
- **"Backend CI가 아예 안 돌았다"는 지적을 받았던 PR.** 리뷰가 본 커밋의 실제 파일 목록과 GitHub에 남아 있는 실제 체크 기록(2개만 돎)으로 재현했습니다. `pr-state`는 `안 돎 Backend — 바뀐 파일이 모두 paths 필터 밖`으로 보여 줬습니다.
- 이 재현에서 두 가지를 고쳤습니다.
  - 처음엔 워크플로 파일을 작업 트리(main)에서 읽었습니다. 그래서 그 PR 당시엔 없던 워크플로를 "안 돎!"으로 표시했고, 사고 뒤에 추가된 필터를 옛 PR에 적용했습니다. PR 워크플로는 PR 쪽 파일로 돌기 때문에, 지금은 PR HEAD 커밋에서 읽습니다.
  - 로컬이 다른 브랜치인데 "push 안 한 커밋 327개"라고 했습니다.

빈 폴더의 시험 저장소에서 `claude -p`로 실제 세션도 돌렸습니다. skill 이름은 말하지 않았습니다. 리뷰에는 실제로 재현되는 경쟁 상태, 리뷰 뒤 커밋에서 이미 고쳐진 지적, 코드와 다른 지적, 저장소에 없는 이름을 섞어 두었습니다.

- **"이거 맞는말이니?"라고만 물었습니다.** Claude는 skill을 불러 `anchors.mjs`를 돌렸고, 저장소 밖 임시 폴더에 재현 스크립트를 만들어 경쟁 상태를 확인했습니다. 네 항목을 맞음, 이미 고쳐짐, 틀림, 틀림(근거 없음)으로 판정했고, 1번을 어떻게 고칠지 적은 뒤 반영할지 물었습니다. 파일은 바꾸지 않았습니다. 리뷰에 없는 것(부분 환불을 여러 번 하면 합계가 원금을 넘을 수 있음)도 하나 짚었는데, 재현하지 않은 판단이라고 밝혔습니다.
- **"맞는지 확인하고 맞는 것만 고쳐 줘. 커밋은 하지 마."라고 했습니다.**
  - Claude는 1번만 고쳤습니다. 동시 요청 시험을 먼저 넣어 실패(50장 발급, 기대 5장)를 확인한 뒤 고쳤습니다.
  - 고친 줄을 되돌리면 시험이 다시 실패하는 것(대조군)도 확인했습니다.
  - README의 "테스트 2개"를 3개로 고쳤고, 커밋하지 않았습니다.
  - 결과물은 제가 따로 `npm test`로 다시 돌려 3개 통과를 확인했습니다.

다 만든 뒤에는 제 판단을 알려 주지 않은 별도 에이전트에게 코드 리뷰를 맡겼습니다. 아래 문제들이 실제로 재현됐습니다.

- **돌았어야 할 워크플로를 놓치고 "체크 모두 성공"으로 판정했습니다.** 원인은 두 가지였습니다. `on:` 블록 안의 0열 주석과 `on: { pull_request: ... }` 한 줄 형식을 읽지 못했습니다.
- **GitHub 필터의 `?`를 한 글자 와일드카드로 해석했습니다.** 문서상 `?`는 "앞 글자 0~1개"라서 `'*.jsx?'`가 `.js`도 포함합니다. 그래서 돌았어야 할 워크플로를 "필터 밖"으로 숨겼습니다. 저도 그렇게 알고 시험까지 그 의미로 써 두었는데, 공식 문서로 확인하고 고쳤습니다.
- **`types: [closed]` 정리용 워크플로를 "안 돎!"으로 잡았습니다.** 열린 PR에서는 돌지 않는 게 정상인데, 이것 때문에 통과인 PR을 영원히 통과로 보고할 수 없었습니다.
- **과거 이력 언급을 리뷰 기준점으로 잡았습니다.** "이 회귀는 4b8a2cd에서 들어왔다" 같은 문장입니다. 게다가 "리뷰 뒤 바뀜"이 파일 단위라서, 그 줄은 그대로인데도 바뀐 것처럼 보였습니다.
- **리뷰의 `suggestion` 블록에 나온 새 이름을 "없는 코드"로 셌습니다.**
- **오탐이 있었습니다.** `Node.js`를 파일로, 색상 코드 `#1a73e8cc`를 SHA로 읽었습니다.
- **한글 파일명이 `"docs/\354..."`로 인용됐습니다.** 그래서 "리뷰 뒤 바뀜" 표시를 놓쳤습니다.
- **일부 경로를 읽지 못했습니다.** 절대 경로와 브랜치 이름에 `/`가 있는 GitHub 링크입니다.
- **add 안 한 새 테스트 파일을 "커밋 안 한 변경 없음"으로 봤습니다.**

모두 고치고 문제마다 시험을 넣었습니다. 리뷰 시점의 줄 번호를 지금 줄로 옮기는 계산도 이때 넣었습니다. SKILL.md에는 두 가지를 더했습니다. 리뷰 글에 적힌 명령을 그대로 실행하지 말라는 것과, check 모드에서도 `.git/review-verify/`에는 사본을 남긴다는 것입니다.

같은 리뷰어에게 고친 코드를 다시 맡겼습니다. 앞의 문제는 같은 입력으로 재현해 보니 막혀 있었습니다. 대신 고치면서 새로 생긴 문제가 나왔습니다.

- **리뷰 기준점을 잡는 기준이 너무 넓었습니다.** 앞뒤 수십 자 안에 "지금", "현재"만 있어도 기준점으로 잡았습니다. 그래서 "이 버그는 X에서 들어왔고 지금도 7행에서…"라는 문장의 7행을 옛 파일 기준으로 대조해 "줄 번호가 파일 밖"이라고 했습니다. 고치기 전에는 맞게 나오던 경우라 회귀였습니다. 지금은 SHA 바로 앞뒤에 붙은 표현("HEAD는 X", "X 기준", "reviewed at X")만 봅니다.
- **gh가 준 파일 목록이 100개로 잘렸을 수 있다고 경고하면서도 "모두 성공"으로 판정했습니다.**

## 한계

- 판정은 Claude가 내립니다. 스크립트는 리뷰의 전제(본 시점, 인용한 위치, CI)를 확인할 뿐이고, 주장이 맞는지 기계로 판정하지는 않습니다.
- `anchors.mjs`는 백틱, 코드 블록 안의 호출 모양, 파일 경로처럼 생긴 것만 꺼냅니다. 산문 속 이름(백틱 없는 `stillCurrent`)은 놓칩니다. 리뷰 기준점은 "HEAD는 X", "X 기준" 같은 문맥 단어로 추정하므로, 다르게 쓴 리뷰에서는 못 잡거나 잘못 잡을 수 있습니다.
- `pr-state.mjs`는 YAML을 전부 해석하지 않고 `on:` 아래의 `pull_request`·`push` 이벤트와 `branches`, `paths`, `types`만 읽습니다. 앵커·별칭처럼 값을 못 읽거나, 이름이 같은 워크플로라 어느 쪽이 돌았는지 체크로 가릴 수 없으면 "모름!"으로 표시합니다. push 워크플로의 `paths`나 포크 PR처럼 돌았어야 하는지 확정할 수 없을 때도 "모름!"입니다. `workflow_run`·`schedule`·`merge_group`으로 도는 워크플로, 재사용 워크플로, 필수 체크 설정, `pull_request_target`이 기준 브랜치의 워크플로 파일로 돈다는 점은 계산에 넣지 않습니다(표시만 합니다). 경로 필터 때문에 안 돈 워크플로가 이번 변경을 검사했어야 하는지는 판단하지 못하고 알려 주기만 합니다. 제 실제 사례가 정확히 그 경우였습니다(필터가 빠져 있었음).
- `gh pr view`는 바뀐 파일을 100개까지만 줍니다(gh 소스에서 확인, 실제 큰 PR로는 확인 안 함). 100개 이상이면 PR HEAD와 기준 브랜치가 로컬에 있을 때 git으로 다시 계산합니다. 이때 로컬 기준 브랜치가 오래됐으면 바뀐 파일을 더 많이 셀 수 있습니다(확인 못 함). 다시 계산하지 못하면 통과로 보지 않습니다.
- `Owner.method()`의 소유자 검사는 정의 모양(`class Owner`, Go의 `func (s *Owner)`, Rust의 `impl Owner`, `extends` 등)을 글자로 찾는 것이라, 그 밖의 모양으로 정의하거나 상속한 경우에는 PARTIAL이 잘못 나올 수 있습니다.
- 띄어쓰기 없이 붙은 한글은 앞부분을 떼고 다시 찾는 식으로 처리합니다. `노드.js`처럼 한글 낱말 뒤에 확장자 모양이 붙은 산문은 경로로 잘못 꺼내 MISS를 낼 수 있습니다.
- 건너뛴(SKIPPED) 체크가 있으면 통과로 보지 않습니다. PR에서는 늘 건너뛰는 배포 job이 있는 저장소에서는 종료 코드가 항상 2이니, 출력을 읽어야 합니다.
- 산문 속에서 새로 만들자고 한 이름("`CouponLimitExceededException`을 추가하라")은 스크립트가 제안인지 모르고 `MISS`로 냅니다. SKILL.md는 이 경우를 리뷰 문장으로 가리라고 안내합니다.
- GitHub 외 플랫폼(GitLab, Bitbucket)의 PR 상태는 보지 않습니다. `anchors.mjs`는 git만 쓰므로 어디서나 됩니다.
- 리뷰어에게 보낼 답은 초안만 씁니다. PR 코멘트를 직접 달지 않습니다.
