# hwpx-deliver

한컴오피스 없이 고객에게 낼 한글 문서(HWPX)와, 같은 모양의 PDF를 함께 만드는 skill입니다. 회의록(클로바노트)·RFP 같은 원자료를 읽어 문장마다 근거를 붙이고, 내기 전에 대화체·자리표시자·원자료와 다른 숫자를 검사합니다. 사용자가 준 HWPX 양식의 칸을 찾아 서식을 그대로 둔 채 채울 수도 있습니다. 지금은 3단계(양식 채우기)까지 되어 있고, 채운 양식의 PDF는 아직 만들지 못합니다.

```
$ node scripts/build.mjs tests/fixtures/doc-long.json --out out --name 계획안
HWPX: out\계획안.hwpx
PDF:  out\계획안.pdf
$ node scripts/check-hwpx.mjs out/계획안.hwpx
구조 오류 없음
```

## 왜 만들었나

공공 사업 일을 하다 보면 결과물을 HWP와 PDF로 함께 내야 하는 경우가 많습니다. 그런데 AI에게 HWP를 만들게 하면 세 가지가 계속 걸렸습니다.

- HWP 파일 자체가 안 만들어지거나, 만들어져도 한컴에서 안 열립니다.
- PDF는 따로 만들어서 HWP와 모양이 다릅니다.
- 대화에서 나온 설명형 문장이 고객 문서에 섞여 나갑니다.

HWPX를 다루는 도구는 이미 있습니다. 한컴 없이 HWPX를 만드는 skill과 라이브러리(hwpx-skills, python-hwpx, kordoc 등)도 있습니다. 이 skill은 **같은 문서 모델 하나에서 HWPX와 PDF를 함께 뽑고, 둘이 한컴에서 같은 모양으로 나오는지를 한컴과 직접 대조해서 맞춘 것**에 무게를 둡니다.

## 어떻게 맞췄나

문서 모델(doc.json)을 HWPX(OWPML)와 인쇄용 HTML로 동시에 바꿉니다. HTML은 Edge·Chrome으로 PDF로 인쇄합니다. 같은 글꼴(함초롬바탕·돋움), 같은 mm·pt 값을 씁니다.

처음 만든 HTML은 한컴이 그린 것과 줄·쪽이 꽤 달랐습니다. 그래서 개발 PC의 한컴오피스 2022로 우리 HWPX를 열고, 한컴이 저장한 PDF와 우리 PDF의 글자 위치를 재서 비교했습니다. 이 과정에서 문서에 없는 한컴의 동작을 여럿 찾았습니다.

- 한글 글꼴의 공백을 글자 크기의 1/2로 그립니다.
- OWPML의 `KEEP_WORD`가 이름과 달리 글자 단위로 끊습니다.
- 글자처럼 취급한 표는 쪽 사이에서 나누지 않습니다.
- 쪽을 넘길 수 있는 표 다음 문단은 위 간격을 잃습니다.
- 쪽을 넘는 표의 바깥 여백을 쪽마다 다시 적용합니다. 그래서 표 위아래 간격은 바깥 여백 대신 표 앞뒤의 빈 간격 문단으로 줍니다.

전체 목록과 측정값은 [tests/oracle/README.md](tests/oracle/README.md)에 있습니다.

그렇게 맞춘 뒤의 대조 결과입니다.

| fixture | 쪽 | 줄 끝 어절이 다른 줄 | 쪽별 첫·마지막 줄 | 기준선 차이 |
|---|---|---|---|---|
| 1쪽 보고서(목록·병합 표), 38줄 | 1 / 1 | 0 | 같음 | 평균 0.14mm |
| 4쪽 계획안(쪽을 넘는 표, 쪽 나누기), 161줄 | 4 / 4 | 2 | 같음 | 평균 0.17mm |
| 2쪽 영문·숫자 혼합(36행 표), 216줄 | 2 / 2 | 0 | 같음 | 평균 0.11mm |

쪽을 넘는 표가 쪽마다 몇 행씩 들어가는지도 한컴과 같고, 쪽 번호("- 1 -") 위치 차이는 0.3mm 이내입니다. 한컴이 우리 HWPX에서 읽어 낸 텍스트는 세 fixture 모두 원래 내용과 한 줄도 다르지 않았습니다. 굵은 글씨, 병합 칸, 칸 음영도 한컴이 다시 저장한 파일에 그대로 남았습니다.

## 원자료와 납품 전 검사

원자료는 번호 붙은 조각으로 나눕니다. 클로바노트 회의록은 발언 하나가 조각 하나입니다.

```
$ node scripts/read-sources.mjs tests/fixtures/src/meeting-clova.txt tests/fixtures/src/rfp.pdf.txt --out work
S1 meeting-clova.txt: transcript, 조각 9개
S2 rfp.pdf.txt: paged-text, 조각 8개
```

Claude는 `work/sources.txt`를 읽고, 문서 모델의 블록과 표 칸마다 근거 조각을 적습니다(`"src": ["S1:3"]`). 원자료 숫자로 계산한 값에는 계산식(`calc`)을, 근거가 없는 내용은 문서 대신 미결 목록(`pending`)에 넣습니다. 이 값들은 고객 파일(HWPX·PDF)에 들어가지 않습니다.

납품 전 검사는 문서 모델을 원자료와 대조합니다. 아래는 `tests/fixtures/doc-sourced.json`에 함정 문장 두 개를 더한 문서의 실제 출력입니다(제목 줄을 빼고 긴 인용을 줄임).

```
$ node scripts/deliver-check.mjs doc-trap.json --sources work/sources.json
오류 3개, 경고 1개, 참고 0개
- [L1 대화·설명형 문장] blocks[12]: 대화체(말씀하신·말씀드린) — "말씀하신 대로 사업비는 1억 3,000만 원으로 정리해 드렸습니다."
- [L1 대화·설명형 문장] blocks[12]: 대화체(정리해 드렸습니다 등) — …
- [N1 원자료와 숫자 대조] blocks[12]: 원자료에 없는 숫자 1억 3,000만 원 (계산한 값이면 calc에 식을 적는다) — …
- [N1 원자료와 숫자 대조] blocks[13]: 인용한 조각(S1:3)에 없는 숫자 45,000명 — S1:4에 있음(src를 고친다) — …
```

| 검사 | 보는 것 |
|---|---|
| L1 대화·설명형 문장 | 말씀하신, 정리해 드렸습니다, 제가, 해요체 끝맺음, 회의록 말투 |
| L2 자리표시자·내부 메모 | `{{ }}`, ○○, TODO, 작성 필요, 확인 필요 |
| L3 군더더기 | 이중 피동, 이모지, 느낌표, 같은 수식어 3번 이상 |
| F1 공문서 표기 | 날짜 온점(2026. 11. 25.), 24시각제(14:30), 천 단위 쉼표. 근거: 「행정업무의 운영 및 혁신에 관한 규정」 제7조제5항 |
| N1 숫자 대조 | 문서의 금액·인원·비율·날짜·시각이 인용한 원자료 조각에 있는지. "1억 2,000만 원"과 "120,000,000원", "6월 30일"과 "2027. 6. 30."은 같은 값으로 봅니다 |
| C1 근거 표시 | 숫자가 있는데 근거가 없는 블록, 없는 조각 id |

`--report` 폴더에는 근거표(문서 조각마다 원자료 발언·문장을 옆에 붙인 표), 미결·확인필요 목록, 검사 결과가 생깁니다. 이미 만든 HWPX(예: 양식을 채운 문서)도 `deliver-check.mjs 문서.hwpx`로 구조와 문장을 검사할 수 있습니다.

## 양식 채우기

양식은 문서마다 다르므로 고정해 두지 않습니다. 받은 양식을 읽어 문단·표·칸마다 주소를 붙이고, 채울 칸 후보를 추정합니다. 아래는 「행정업무의 운영 및 혁신에 관한 규정 시행규칙」 별지 제1호서식(기안문)을 한컴으로 HWPX 저장한 것을 읽은 실제 출력의 일부입니다.

```
$ node scripts/scan-template.mjs tests/fixtures/forms/form1-giannmun.hwpx
    T1.r2c1 (1x15 병합)
      T1.r2c1.p1: "행 정 기 관 명"
      T1.r2c1.p3: "수신"
      T1.r2c1.p5: "제목 "
    T1.r3c1 (1x15 병합)
      T1.r3c1.p1~p20: (빈 문단 20개)
      T1.r3c1.p22 [개체]: ""
        T1.r3c1.T2: 표 1행 1열
          T1.r3c1.T2.r1c1
            T1.r3c1.T2.r1c1.p1: "발신명의"
# 채울 칸 후보
- T1.r2c1.p5: 항목 이름 뒤에 적는 칸(추정) "제목"
- T1.r11c1.p1: 서식 안내문(제출본에서 지울지 확인) "비고(이 난은 서식에 포함하지 아니한다)"
- T1.r3c1: 본문 자리(빈 문단) 빈 문단 20개
- T1.r6c2: 항목 이름 옆 빈 칸(추정) "협조자"
```

Claude는 이 지도를 보고 fill.json을 씁니다. 지원하는 작업은 다섯 가지입니다.
- 칸이나 문단의 글자 바꾸기
- 글자를 찾아 바꾸기("행 정 기 관 명" → 기관명)
- 반복 행 채우기(모자라면 행을 복제해 늘림)
- 행 지우기
- 다른 문단 모양 빌리기(`like`)

`fill-template.mjs`가 양식의 글자 모양·문단 모양·표 크기는 그대로 두고 값만 넣습니다. 바꾼 문단은 한컴이 줄 배치를 다시 계산하도록 줄 배치 정보(`linesegarray`)를 지웁니다.

한컴 2022로 열어 확인한 것:
- 기안문: 머리 줄·안내 행 지우기, 용어 바꾸기, 본문 6줄, 하위 표(발신명의) 안 글자. 1쪽으로 열리고, 한컴이 읽은 텍스트가 넣은 값과 같습니다.
- 대장(빈 행 4개 + 합계 행): 6행을 넣으면 2행이 늘고 합계 행이 아래로 밀립니다. 머리 행 서식과 테두리는 그대로입니다.

양식 채우기에서 드러난 것도 고쳤습니다. 표 안에 표가 있는 양식에서 HWPX 읽기가 바깥 표의 칸 글자를 문단 글자로 새게 하고, 하위 표의 칸 주소를 바깥 칸 주소로 잘못 읽고 있었습니다. 2단계 원자료 읽기도 같은 코드를 씁니다.

### 다시 검증하기

코드를 처음 보는 에이전트 두 명에게 검증을 나눠 맡겼습니다. 한 명은 양식 채우기를 한컴 대조까지 포함해 보고, 다른 한 명은 읽기와 납품 전 검사를 봤습니다. 실제로 재현한 결함만 보고하게 했고, 18건이 나왔습니다. 모두 고쳤고, 에이전트가 남긴 재현 사례를 고친 코드로 다시 돌려 결과가 바뀐 것을 확인했습니다(고치기 전에 직접 재현해 본 것은 그중 절반가량입니다). 큰 것만 적습니다.

- 머리말·글상자가 든 문단에 값을 넣으면 값이 머리말·글상자 안으로 들어갔습니다. 표만 떼어 두고 다른 하위 글(`subList`)은 문단 글자로 다뤘기 때문입니다.
- 한컴은 탭과 줄바꿈을 `<hp:t>회의명:<hp:tab …/>{{회의명}}</hp:t>`처럼 글자 요소 안에 저장합니다. 읽기에서는 탭이 사라졌고, 채우기에서는 "회의명:〈탭〉{{회의명}}" 양식을 채우지 못했습니다.
- 합계 행이 데이터 행과 같은 모양이면 반복 행 채우기가 합계 행을 덮어썼습니다.
- 첫 문단에 여러 줄을 넣으면 구역 설정이 복제되어 쪽이 나뉘었습니다.
- 본문이 넘치면 넘친 줄이 직인 상자 아래로 갔습니다.
- 위에서 세로로 병합된 칸이 걸친 행을 복제하면 표에 구멍이 생겼습니다.
- 값에 `$&`가 있으면 XML이 깨졌습니다.
- 시각이 붙은 일정표를 회의록으로 읽었습니다.
- 숫자 대조가 "10부"·"3식" 같은 제출 부수를 건너뛰었습니다.

고친 결과는 한컴 2022로 열어 확인했습니다. 결함마다 회귀 시험을 넣었고, 고친 곳을 되돌리면 해당 시험이 실패합니다. 예외가 하나 있습니다. 숫자 `find` 검사는 두 곳에서 막고 있어서, 한 곳만 되돌리면 다른 곳이 멈춥니다.

## 사용법

```
cp -r hwpx-deliver ~/.claude/skills/
```

"이 회의록으로 결과 보고서 써줘"처럼 원자료 파일과 함께 요청하면, Claude가 원자료를 읽고 근거를 붙여 doc.json을 쓰고, 빌드와 납품 전 검사까지 합니다. "이 양식에 회의록 내용 채워줘"처럼 HWPX 양식을 함께 주면, 채울 칸 목록과 넣을 내용을 먼저 보여 주고 확인받은 뒤 채웁니다(양식이 .hwp면 한컴에서 HWPX로 저장해서 줍니다). 이미 있는 HWPX만 검사하려면 `/hwpx-deliver check 파일.hwpx`라고 하면 됩니다.

Node.js와 Edge 또는 Chrome이 필요합니다. 글꼴은 함초롬바탕·함초롬돋움을 씁니다(한컴오피스나 한컴 무료 글꼴로 설치). 문서가 쓰는 글꼴이 없으면 다른 글꼴로 대체하지 않고 멈춥니다.

## 시험

```
node tests/run-tests.mjs
```

시험은 172개이고 한컴 없이 돕니다. 한컴 대조 결과(한컴이 읽은 텍스트, 작성자 정보를 지운 한컴 저장본)는 저장소에 넣어 두었습니다. 원자료 시험 자료(회의록, 제안요청서)는 지어낸 내용입니다. DOCX·XLSX 시험 파일은 시험 안에서 만듭니다. 양식 시험 자료는 법령 별지 서식(저작권법 제7조에 따라 보호 대상이 아님)의 원본 HWP와 그것을 한컴으로 HWPX 저장한 것, 그리고 직접 만든 대장 양식을 한컴으로 다시 저장한 것과 그 변형 5개(머리말, 글상자, 탭, 합계 행이 같은 모양, 위에서 세로 병합)입니다. 마지막 저장자 정보는 지웠습니다.

아래 동작을 하나씩 되돌리면 해당 시험이 실패하는 것을 확인했습니다.

- 1단계(한컴과 모양 맞추기): 어절 단위 줄 나눔, 쪽을 넘기는 표, 내어쓰기, 굵은 글씨, 표 바깥 여백 0과 표 앞뒤 간격 문단, 칸 문단 보정을 위쪽 여백으로, 칸 여백에서 테두리 두께 빼기
- 2단계(원자료와 검사): 오전·오후 시각 읽기, 연도 없는 날짜("6월 30일") 대조, 항목 이름 칸을 근거 검사에서 빼기, DOCX 세로 병합 칸, 계산식만 있는 블록의 숫자 검사, 회의록 머리말(일시·작성자) 조각, 클로바노트 꼬리말 빼기, 작성자·시간을 뺀 회의록을 빈 줄로 나누기, 작성자만 넣은 모양
- 3단계(양식): 하위 표가 있는 칸의 주소, 바깥 문단에서 표를 깊이 맞춰 빼기, 바꾼 문단의 줄 배치 정보 지우기, 행을 늘린 뒤 아래 행 주소 밀기(시험 중 예외로 잡힘), 행 수 갱신, `like`가 하위 표를 건드리지 않기, run에 나뉜 글자 바꾸기, 그리고 "다시 검증하기"의 고친 곳들

- 표 행 높이가 행마다 ±0.25mm 어긋납니다. 브라우저가 1/96인치 단위로 맞추기 때문입니다. 대조한 표(36행)에서는 오차가 쌓이지 않았지만, 행이 쪽 끝에 아슬아슬하게 걸치면 다르게 나눌 수 있습니다.
- 쪽 번호는 아래 가운데만 됩니다.
- 줄 폭에 아슬아슬하게 맞는 줄은 한컴과 다른 어절에서 끊길 수 있습니다.
- 한컴에서 열리는지는 한컴 없이 100% 확인할 수 없습니다. 구조 검사는 알려진 원인만 잡습니다.
- 클로바노트 회의록: 작성자·시간을 둘 다 넣은 것과 둘 다 뺀 것은 실제 내보내기 파일 7개로 확인했습니다(발언 수가 원문과 같음, 꼬리말 제거). 하나만 넣은 모양은 실제 파일로 확인하지 못해, 지어낸 형식으로만 시험합니다. 실제 파일은 업무 통화라 저장소에 넣지 않았고, 시험 자료는 같은 모양으로 지어낸 것입니다.
- 회의록의 음성 인식 오류(같은 대상이 다르게 적힘, 잘못 들은 숫자)는 검사로 잡지 못합니다. 잘못 인식된 숫자를 옮겨도 숫자 대조는 통과합니다.
- PDF는 스크립트가 읽지 않습니다. Claude가 읽고 쪽 표시를 붙여 텍스트로 옮긴 것을 원자료로 씁니다.
- 숫자 대조는 숫자가 인용한 조각에 있는지만 봅니다. 그 숫자가 무엇의 값인지는 근거표를 보고 판단해야 합니다.
- 문장 검사는 정해 둔 표현만 잡습니다. 공문서 항목 기호 순서와 금액 한글 병기는 검사하지 않습니다.
- 양식 채우기는 글자만 넣습니다. 새 글자 모양(굵게 등)은 만들지 않습니다. 글자 폭을 재지 않아서, 고정 크기 칸에서 넘치는지는 "원래보다 N자 길어짐" 경고로만 알립니다. 시험한 기안문의 발신명의 상자는 기관장 이름을 넣으면 두 줄로 접혔습니다.
- 채울 칸 후보는 추정입니다. 양식마다 쓰는 방식이 달라서, 양식 지도를 사람이(또는 Claude가) 읽고 정해야 합니다. 시험한 양식은 기안문 하나, 직접 만든 대장 하나, 그리고 대장의 변형 5개뿐입니다. 누름틀은 찾기만 하고 실제 누름틀 양식으로 시험하지 않았습니다.
- 미리보기 그림(`Preview/PrvImage.png`)은 만들지 못해 빈 양식 그림 그대로 남습니다. 미리보기 글은 채운 내용으로 바꿉니다.
