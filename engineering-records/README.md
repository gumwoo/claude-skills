# engineering-records

작업이 끝났을 때 트러블슈팅·성능 개선·설계 결정 기록을 남길지 판정하고, 남긴다면 저장소에 이미 있는 규칙(번호, 템플릿, 목록 파일)대로 쓰는 skill입니다. 쓴 문서의 숫자가 측정 원자료와 맞는지도 검사합니다.

문서의 측정 숫자 뒤에 원자료 위치를 주석으로 달아 두면, 검사기가 그 파일에서 값을 꺼내 대조합니다. 렌더링된 문서에는 주석이 보이지 않습니다.

```markdown
| p95 | 850ms <!-- src: ../../benchmarks/search-before.json :: metrics.http_req_duration.values["p(95)"] --> | 210ms <!-- src: ... --> | -75% |
```

숫자가 몇 개 틀린 개선 문서를 검사하면 이렇게 나옵니다(일부).

```
$ node scripts/verify-numbers.mjs docs/improvements/IMP-002-bad-numbers.md

  출처 표시 8개 중 6개 확인 · ERROR 5 · WARN 2
  ERROR    6행  문서 900 ≠ 원자료 849.6 (../../benchmarks/search-before.json :: metrics.http_req_duration.values["p(95)"])
  ERROR    7행  출처 파일이 없습니다: ../../benchmarks/nope.json
  ERROR    8행  변화 "+40,000%"가 before 118 req/s → after 1,381 req/s와 맞지 않습니다(계산 +1070.3%)
  WARN     8행  출처 없는 숫자 118, 1,381: 원자료를 <!-- src: 파일 :: 경로 -->로 달거나, 실측이 아니면 "예측"이라고 적으세요
  ERROR    9행  변화 "-90%"가 before 37건 → after 0건와 맞지 않습니다(계산 -100.0%)
  WARN    13행  출처 없는 숫자 0.4: 원자료를 <!-- src: 파일 :: 경로 -->로 달거나, 실측이 아니면 "예측"이라고 적으세요
```

## 사용법

```
git clone https://github.com/gumwoo/claude-skills.git
cp -r claude-skills/engineering-records ~/.claude/skills/
```

설치해 두면 장애 원인을 찾았거나, 전후를 측정했거나, 설계를 정한 뒤 "문서로 남겨", "기록할 거 없어?"라고 할 때 Claude가 씁니다. 직접 부를 수도 있습니다.

```
/engineering-records                                   # 판정하고, 필요하면 쓰고 검사
/engineering-records check docs/improvements/IMP-012-cache.md   # 숫자 검사만
/engineering-records install-hook local observe        # 작업 끝 알림 hook 설치
```

skill은 판정, 규칙 읽기, 쓰기, 검사, 보고 순서로 진행합니다. 판정의 기본값은 "쓰지 않음"이고, [references/criteria.md](references/criteria.md)의 기준에 걸릴 때만 후보로 올립니다. 규칙은 `scripts/scan.mjs`가 저장소에서 읽습니다. `TS-001-slug.md`, `adr-0003-x.md`, MADR식 `0001-title.md` 같은 이름에서 폴더별 접두어, 다음 번호, 템플릿, 목록 파일을 찾아냅니다. 기록 문서가 하나도 없는 저장소면 `templates/`의 기본 템플릿을 씁니다.

hook을 설치하면 작업이 끝날 때 이번 세션에 측정 명령(k6, hyperfine, EXPLAIN 등)을 돌렸거나, 측정 원자료나 마이그레이션 같은 설계 파일을 바꿨는데 기록 문서는 쓰지 않은 경우를 알려 줍니다. 기본(observe)은 한 줄 알림만 띄우고 막지 않습니다. nudge는 Claude가 한 번 더 이어서 기록이 필요한지 판정하게 합니다. 세션마다 한 번만 알립니다.

Node.js 22 이상만 있으면 되고 외부 패키지는 없습니다.

## 만들면서 고민한 것

이 skill은 제 작업 기록에서 나왔습니다. 개인 프로젝트에서 Claude Code에 직접 입력한 요청 약 1,800건을 유형별로 묶어 보니, 트러블슈팅·개선·결정 문서를 써 달라는 요청이 약 100건이었습니다. 거의 매번 제가 먼저 "문서로 남길 거 없어?"라고 꺼내야 했고, 반복해서 지적한 내용도 비슷했습니다. 수치가 서로 섞였다, 실측해서 남겨야 한다 같은 것들이었습니다. 표에 "+40,000"이라고 적었는데 실측은 +6,422였던 적도 있습니다.

찾아보니 문서화 skill은 이미 많았습니다. 대화에서 ADR을 만들어 주는 [auto-adr](https://github.com/tanRdev/auto-adr), 장애 회고 skill들, 작업이 끝나면 기록할 만한지 평가해 일지 저장소에 남기는 Engineering Journal, 결정 기록의 번호와 목록을 Rust CLI로 관리하는 [living-docs](https://github.com/ejklock/living-docs-skill) 같은 것들입니다. 그런데 문서 속 숫자가 원자료와 맞는지 기계로 확인하는 것은 찾지 못했습니다. 그래서 그 부분을 이 skill의 중심에 두었습니다.

판정 기준은 실무 자료에서 가져왔습니다. 트러블슈팅은 Google SRE의 포스트모템 기준(사용자에게 보이는 장애, 데이터 유실, 사람의 개입, 오래 걸린 해결)을 따랐고, "검색 몇 분이면 푸는 설정 누락은 쓰지 않는다"를 더했습니다. 결정 기록은 Spotify와 AWS 가이드의 범위(구조, 비기능 요구, 의존성, 인터페이스)를 따랐습니다. 확정된 결정은 고치지 않고 새 기록으로 대체한다는 규칙도 AWS 가이드에서 가져왔습니다. 모든 작업을 문서로 만들면 결국 아무도 읽지 않으니, 기본값은 "쓰지 않음"으로 했습니다.

알림 hook은 막지 않는 쪽으로 만들었습니다. 첫 번째 skill(new-project-setup)의 hook을 만들 때와 같은 이유입니다. 문서를 안 쓰면 끝내지 못하게 막으면, 결국 꼭 필요 없는 문서까지 쓰게 됩니다.

## 어떻게 확인했나

`node tests/run-tests.mjs`로 121개 시험을 돌립니다. 시험은 임시 폴더에 가상의 저장소를 만들어 씁니다. 그 저장소에는 트러블슈팅·개선·결정 문서, k6 summary 형식의 벤치 JSON, 텍스트 로그가 들어 있습니다.

제 개인 프로젝트에도 읽기 전용으로 돌려 봤습니다.

- 스캐너는 트러블슈팅 57개, 개선 54개, 결정 31개와 각각의 다음 번호, 템플릿, 목록 형식을 맞게 읽었습니다.
- 기존 개선 문서 사본에 원자료 표시를 달고 실제 벤치 파일과 대조하자 통과했습니다. 숫자 하나를 바꾸면 원자료 불일치와 변화율 불일치를 둘 다 잡았습니다.
- 트러블슈팅·개선·결정 문서 142개 전체에 검사기를 돌리자 처음엔 변화율 오류가 3건 나왔습니다. 확인해 보니 셋 다 검사기 쪽 오탐이었습니다. `9m46s (586s)`를 9와 3으로 읽었고, `0.498 / 0.482 / 0.426`처럼 한 칸에 실행별 값을 적은 것을 첫 값으로만 계산했습니다. 시간 표기를 초로 바꾸고 여러 값 중 하나라도 맞으면 통과하게 고친 뒤에는 0건입니다.

빈 폴더에서 `claude -p`로 실제 세션도 두 번 돌렸습니다. skill 이름은 말하지 않았습니다.

- **N+1 문제를 고치고 전후 측정 파일을 남긴 저장소에서 "문서로 남길 게 있으면 정리해 줘"라고 했습니다.**
  - Claude는 skill을 불러 개선 기록만 "씀"으로 판정했습니다. 근거는 두 측정 파일의 조건(VU, 시간, 데이터량)이 같고 p95가 -87%라는 점이었습니다. 트러블슈팅과 결정 기록은 이유를 붙여 "안 씀"으로 판정했습니다.
  - 기존 번호와 목록 형식을 따라 문서를 썼고, 숫자 10개에 원자료 표시를 달았습니다. 검사 결과는 10개 일치였습니다.
  - 원자료에 없는 워밍업과 반복 횟수는 "측정 안 함"으로 적었습니다.
  - 제가 결과 문서를 따로 다시 검사해도 ERROR 0, WARN 0이었습니다.
- **README 문구 하나만 고친 저장소에서 "기록할 거 있어?"라고 했습니다.** Claude는 `git diff`를 확인한 뒤 세 종류 모두 "안 씀"으로 판정하고 끝냈습니다.

다 만든 뒤에는 제 판단을 알려 주지 않은 별도 에이전트에게 코드 리뷰를 맡겼습니다. 그 결과 검사기가 숫자를 놓치는 경우가 여러 개 실제로 재현됐습니다.

- `**850ms** <!-- src -->`처럼 숫자와 표시 사이에 굵게 표시가 끼면, 표시 자체가 검사되지 않았습니다.
- 1000→500인데 "50% 증가"라고 써도 통과했습니다.
- "전체 요청" 열을 before 열로 잘못 잡았습니다.
- "unexpected"가 "expected"(예측 표시)에 걸려 그 줄의 숫자를 건너뛰었습니다.
- 7자리 이상 정수를 커밋 해시로 보고 지웠습니다.
- 목록에 IMP-10만 있는데 IMP-1이 "있음"으로 판정됐습니다.

모두 고치고 문제마다 시험을 하나씩 추가했습니다. 고친 뒤 실제 프로젝트 문서에 다시 돌리다가, 제목에 "조건"이 들어간 결과 절("결과 (재측정, 동일 조건)")이 통째로 검사에서 빠지는 문제를 하나 더 찾았습니다.

같은 리뷰어에게 고친 코드를 다시 맡겼더니, 앞의 문제들은 재현으로 막힌 것이 확인됐습니다. 대신 고치면서 새로 생긴 문제가 나왔습니다. 열 이름을 칸 전체로만 맞추도록 바꾸면서 `수정 전`이나 `Before p95` 열을 못 알아봐, 틀린 변화율이 다시 통과하고 있었습니다. 목록 파일 본문에 `75% 감소`처럼 `%`가 하나라도 있으면 URL 디코딩이 통째로 실패하는 문제도 있었습니다. 이것들도 고치고 시험을 더했습니다.

마지막으로 앞의 리뷰를 모르는 새 리뷰어에게 처음부터 다시 맡겼습니다. 흔한 한국어 표 작성 방식에서 놓치는 경우가 더 나왔습니다. `전(ms)`처럼 괄호가 붙은 열 이름, `▲75%` 같은 방향 표시, 앞에 `|`가 없는 표, 인용 안의 표, 대문자로 쓴 `<!-- SRC: -->` 같은 것들입니다. 문서는 %인데 원자료가 0~1 비율이면 반올림으로 우연히 맞는 경우도 있었습니다. 표 인식을 GFM 규칙(머리 행 다음 줄이 구분선)으로 다시 짜고, 나머지도 고쳐 시험에 넣었습니다. 스캐너는 log4brains의 날짜형 이름, MADR의 `0000-template.md`, 설명만 있는 README, 링크 없이 ID만 적은 목록, monorepo의 서비스별 adr 폴더를 잘못 읽고 있어서 함께 고쳤습니다.

알림 hook은 실제 Claude Code 세션에 설치해서도 확인했습니다. 기록 얘기는 하지 않고 "Set 탐색으로 바꾼 효과를 전후로 재 줘"라고만 했습니다.

- 처음에는 hook이 알림을 놓쳤습니다. 벤치 스크립트가 인자로 받은 경로에 결과를 쓰면, 세션 기록에는 그 파일이 남지 않기 때문입니다. 그래서 git 작업 트리의 새 파일도 함께 보게 고쳤습니다.
- 고친 뒤 nudge 모드에서는 측정이 끝나자 hook이 한 번 막았습니다. Claude는 skill을 불러 "개선 기록 후보, 나머지는 쓰지 않음"으로 판정하고, 쓰기 전에 "코드 변경이 실제로는 없고 반복 측정도 안 했다"는 점을 들어 먼저 물었습니다.
- observe 모드에서는 사용자에게 알림 한 줄만 띄웠습니다.

## 한계

- 원자료 표시를 단 숫자만 원자료와 대조합니다. 표시가 없는 숫자는 측정 맥락(before/after 표, 결과·측정 절)에 있을 때만 "출처 없음"으로 알리고, 다른 곳의 숫자는 보지 않습니다.
- 변화율은 같은 행의 숫자만 보고 계산합니다. 한 행에 단위를 섞어 쓰면(1.2s와 310ms) 틀린 계산이 나옵니다.
- 판정은 Claude가 기준 문서를 읽고 내립니다. 경계에 있는 작업은 skill이 사용자에게 묻도록 했지만, 판정 자체를 기계로 검증하지는 않습니다.
- 알림 hook은 세션 기록 끝부분(8MB)과 git 작업 트리의 커밋 안 된 파일을 보고, 이름 규칙으로 기록 문서를 알아봅니다. 아주 긴 세션의 앞쪽에서 쓰고 이미 커밋한 기록이나, 규칙 밖의 이름으로 쓴 기록은 놓칠 수 있습니다. 작업 트리에 전부터 남아 있던 벤치 파일 때문에 알림이 날 수도 있습니다.
- 노션 같은 외부 도구로 보내기, 작업 일지, 면접 질문 만들기는 다루지 않습니다.
